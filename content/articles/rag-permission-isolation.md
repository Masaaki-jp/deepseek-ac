## リード

原文に部署ごとの権限があっても、検索索引とキャッシュが全社で1つなら回答は漏れます。
漏れる経路は「検索」と「キャッシュ」の2本、防ぐ場所は生成の前です。
この記事では、セット分割（テナント分離）を軸に、検索・再利用・権限更新の3点を設計します。

## 前提

- 想定読者: 社内文書RAGを構築・運用するエンジニア、情報システム担当
- 必要な環境: Python 3.10+、DeepSeek API キー（サーバー側のみ）、ベクトルDB（メタデータフィルタ対応のもの）
- 前提知識: RAGの基本構成、OpenAI互換SDKの呼び出し、社内のAD/SSOグループ運用

## 本文

### 漏れる経路は2本ある

**経路1：検索索引。** 全部署の文書が1つのベクトルDBに混ざっていると、営業の質問に対して経理・人事の文書がヒットします。そのチャンクはそのままプロンプトに入り、回答として返ります。原文を開く権限がなくても、内容は届いてしまいます。

**経路2：共有キャッシュ。** キャッシュが全員で1つだと、経理部への回答が保存され、同じような質問をした別部署の人物にそのまま返ります。この経路は検索もモデルも通りません。

OWASP の LLM08:2025（Vector and Embedding Weaknesses）は、共有ベクトルDBにおける cross-context leak を中核リスクとして挙げ、権限を意識したストアと利用者グループ間の厳格な分割を推奨しています。

要点は「原文の権限は部署ごとなのに、索引とキャッシュは全社で1つ」という非対称です。境界のない場所を通って情報が外に出ます。

### モデルへの禁止指示では代替できない

| | 禁止指示 | セットで隔離 |
|---|---|---|
| 他部署の文書は検索で手に入るか | 入る（同じDB） | 入らない（別DB） |
| モデルに渡るか | 渡る。その上で「言うな」と頼む | そもそも渡らない |
| 確実さ | モデル次第（言い換え・要約・注入で破られうる） | 構造的に確実 |
| キャッシュ経路 | 効かない（モデルを通らない） | 別キャッシュなので起きない |

禁止指示は「情報が手元に届いた後で頼む」対策です。はい/いいえで推測させる、要約させる、文書内に仕込まれた指示に従わせる、といった迂回路が残ります。加えてキャッシュ経路には指示を置く場所自体がありません。

したがってアクセス制御は構造で行い、禁止指示は「根拠にない内容を推測しない」といった補助に限定します。

### 設計①：検索をセットで分ける

部署（または機密区分）ごとに、ベクトルDB・アプリ・キャッシュを1セットにします。各セットにはその部署の文書だけを取り込み、人事のような極秘はどのセットにも入れません。どのセットに入れるかはADグループ＋SSOで決め、APIキーはサーバー側だけで保持してクライアントに渡しません。

```python
# retrieval.py
from dataclasses import dataclass

@dataclass(frozen=True)
class Principal:
    user_id: str
    tenant: str              # 部署ID = セットID
    groups: frozenset[str]   # ADグループ = 閲覧可能な機密区分

def retrieve(query: str, p: Principal, store, top_k: int = 5) -> list[dict]:
    """質問者の権限で絞ったチャンクだけを返す。生成前の唯一の防衛線。"""
    if not store.user_has_set_access(p.user_id, p.tenant):
        raise PermissionError("no access to this set")

    return store.search(
        query=query,
        tenant=p.tenant,                              # セット境界（物理 or namespace）
        top_k=top_k,
        filter={"acl": {"$in": sorted(p.groups)}},    # 文書側ACLとの積集合
    )
```

セットを物理的に分けるか、1つのDB内で namespace＋メタデータフィルタで分けるかはトレードオフです。

| 方式 | 漏れにくさ | 運用コスト | 細かい権限 |
|---|---|---|---|
| セット分割（物理） | 高 | 高（セット数分のDB・キー・キャッシュ） | 弱い |
| メタデータACLフィルタ（論理） | 実装依存（フィルタ漏れ＝全漏れ） | 低 | 強い |
| 併用 | 高 | 中 | 強い |

セット方式は「課長だけ」「この案件の担当者だけ」といった同一部署内の細分化を表現できません。そこは文書ごとのACLメタデータで補い、セットは部署単位の粗い境界として使うのが現実的です。

### 設計②：キャッシュもセットに閉じる

キャッシュのキーにテナントと権限集合を含めます。ここを「正規化した質問文だけ」にすると、経路2がそのまま再現されます。

```python
# cache.py
import hashlib

def cache_key(p: Principal, query: str) -> str:
    norm = " ".join(query.split()).lower()
    q = hashlib.sha256(norm.encode()).hexdigest()[:16]
    acl = hashlib.sha256(",".join(sorted(p.groups)).encode()).hexdigest()[:8]
    return f"ans:{p.tenant}:{acl}:{q}"   # tenant/ACLを外すと別部署に流れる
```

会話履歴とログもセット単位で保管します。TTLは必須で、権限変更や文書削除に追従できる長さ（例：1時間）にします。

### 設計③：権限更新と削除をセットに反映する

```python
# pipeline.py（概念）
def answer(query: str, p: Principal, store, cache, llm) -> str:
    key = cache_key(p, query)
    if (hit := cache.get(key)) is not None:
        return hit

    chunks = retrieve(query, p, store)   # 権限外はここで既に落ちている

    resp = llm.chat.completions.create(
        model="deepseek-chat",           # モデル名・料金は公式ドキュメントで要確認
        messages=[
            {"role": "system", "content": "与えられた根拠のみに基づいて答える。根拠にない内容は「不明」と答える。"},
            {"role": "user", "content": render(query, chunks)},
        ],
    )
    out = resp.choices[0].message.content
    cache.set(key, out, ttl=3600)
    audit_log(p, p.tenant, [c["id"] for c in chunks], resp.id)
    return out
```

- **人の異動**：ADグループから外せばそのセットにログインできなくなります。権限をADの1点で管理できるのがセット方式の利点です
- **文書の移動・権限変更**：旧セットのDBとキャッシュから削除し、新セットへ取り込み直す
- **文書の削除**：DBとキャッシュの両方から削除する
- **定期突き合わせ**：「原文の置き場所・権限」と「どのセットに入っているか」を比較するバッチを回す
- **監査ログ**：誰が・いつ・どのテナントで・どのチャンクを引き・何を生成したか。規制対応の監査では事後の再構成ではなく、経路に組み込んだ記録が求められます

クライアント初期化はサーバー側のみで行います。

```python
import os
from openai import OpenAI

llm = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],   # .envはコミットしない
    base_url="https://api.deepseek.com",
)
```

## つまずきポイント

| 症状 | 対処 |
|---|---|
| 営業の回答に経理の数字が混ざる | 索引が全社共有。tenantで分割し、検索時にACLフィルタを必須化 |
| 別部署の人物に同じ回答が返る | キャッシュキーに tenant / ACL が入っていない |
| 異動後も元部署の文書が引ける | セットアクセスをADグループ連動にし、キャッシュTTLを短縮 |
| 全社公開に変えた文書が出ない／出続ける | 旧セットから削除→新セットへ再取り込み。キャッシュも無効化 |
| 「社内情報は出力しないで」と書いたのに漏れる | 生成前の検索で絞る。指示は補助に留める |
| フィルタを足したら検索精度が落ちた | 権限フィルタ後の候補で再ランキングする（top_kを広げてから絞る） |

## まとめ

- 漏れる経路は「検索索引」と「共有キャッシュ」の2本。どちらも生成前の構造で塞ぐ
- 禁止指示は経路2に届かず、経路1でも迂回される。アクセス制御の代わりにはならない
- セット分割＋メタデータACLの併用で、粗い境界は物理的に、細かい権限は論理的に守る
- 異動・文書移動・削除をセットへ反映する運用手順と監査ログまで含めて設計とする
