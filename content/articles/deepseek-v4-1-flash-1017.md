## リード

V4.1-Flash-1017 は V4.1-Flash のマイナーアップデート。ただしベンチマークの伸び幅は小さくなく、特にエージェント系タスクで改善が大きい。乗り換える価値があるかを数値ベースで判断できるように整理する。

## 前提

- 想定読者: DeepSeek API を使っている・検討中のエンジニア
- 必要な環境: なし（比較・評価が目的）
- 前提知識: LLM のベンチマーク指標（HLE / Terminal-Bench など）の意味

## 本文

### V4.1-Flash からの変更点

公式の位置づけは「V4.1-Flash の小幅更新」。ただし以下が改善している。

- 推論・コーディング・エージェントタスク・視覚ベンチマーク全般でスコア向上
- **タスク実行時間と出力長を短縮**（コスト・レイテンシ削減）
- エージェント評価で「性能とコストのパレートフロント」を前進

「小幅更新だが、安く速くなった」というのが要点。**同じワークロードなら乗り換えでコストが下がる可能性がある**。

### ベンチマーク比較（主要指標）

資料の数値から、特に差が大きいものを抜粋する。

| 指標 | V4.1-Flash-1017 | V4.1-Flash | 差分 |
|---|---:|---:|---:|
| HLE（no tools） | 42.6 | 36.8 | **+5.8** |
| Terminal-Bench 4.0 | 42.3 | 31.2 | **+11.1** |
| ProgramBench | 29.1 | 20.3 | **+8.8** |
| Apex Bench v1.1 | 72.1 | 64.6 | **+7.5** |
| Automation-Bench v1.0.6 | 60.5 | 54.8 | **+5.7** |
| NL2Repo-Bench | 68.2 | 65.4 | +2.8 |
| DeepSWE v1.1 | 77.0 | 74.2 | +2.8 |
| Agents' Last Exam | 35.4 | 31.8 | +3.6 |
| Chartography（with tools） | 83.0 | 78.9 | +4.1 |
| BabyVision（with tools） | 92.5 | 89.6 | +2.9 |
| ZeroBench-main（with tools） | 51.0 | 49.0 | +2.0 |

**エージェント・コーディング系（Terminal-Bench, ProgramBench, Apex Bench）の伸びが顕著**。逆に汎用画像系（BabyVision, ZeroBench）は伸びが小さい＝元から高水準で頭打ち気味。

### 競合他社との相対位置

資料には K3 / GLM-5.3 / GPT-5.6 Sol / Opus 5 の数値も併記されている。

- **Terminal-Bench 4.0**: 42.3 は Opus 5（51.8）、GPT-5.6 Sol（39.9）と Opus 5 に次ぐ位置。K3（12.6）・GLM-5.3（37.9）を上回る
- **Apex Bench v1.1**: 72.1 は Opus 5（65.8）を上回る
- **HLE（no tools）**: 42.6 は Opus 5（56.3）に劣るが、GPT-5.6 Sol（44.5）には迫る
- **NL2Repo-Bench**: 68.2 は Opus 5（75.3）に次いで 2 位

**総じて「Opus 5 に次ぐが一部タスクでは逆転」**というポジション。コスト次第では Opus 5 の代替になり得る。

### 推奨サンプリングパラメータ

公式に記載されている値。

| パラメータ | 推奨値 |
|---|---|
| temperature | 1.0 |
| top_p | 1.0 |
| context_window | 1,000,000 tokens（100万） |
| max_tokens | ≥ 256K |

**コンテキスト窓 100 万トークン**は実用上大きなポイント。長文 RAG・大規模リポジトリ解析で効いてくる。

### プロンプトエンコーディングと再現手順

公式リポジトリには以下が含まれる。

- `encoding/encoding.py`: Jinja テンプレートではなく **Python リファレンス実装**。多輪会話・ツール呼び出し・思考モード・数値推論強度・会話途中の system メッセージ・画像テキスト混在のテストケース付き
- `deepseek-recipe`: Rust + Python バインディングのプロトコル対応ツールキット。Messages / Chat Completions / Responses API を Conversation 形式に変換し、V4 / V4.1 プロンプトまたは Token ID へエンコード、出力のパースまで担当
- `inference/`: 重み変換とローカル推論の手順

**自前でプロンプトを組み立てる場合は `encoding.py` を参照実装として使うのが安全**。Jinja テンプレートがないので、テンプレートベースの既存ワークフローは調整が必要になる可能性がある。

### ライセンス

## つまずきポイント

| 症状 | 対処 |
|---|---|
| Jinja テンプレートが見つからない | 本バージョンには未収録。`encoding.py` か `deepseek-recipe` を使う |
| 既存プロンプトで挙動が変わる | temperature=1.0 / top_p=1.0 推奨値に揃える。旧 Flash 用に調整した値は見直す |
| コンテキスト窓を活かせない | 100 万トークン対応だが、API 側の上限は別途公式で要確認 |
| 出力長が短くなった気がする | 仕様変更の可能性あり。プロンプトで明示的に長さを指示する |

## まとめ

- V4.1-Flash-1017 は V4.1-Flash の改良版で、特にエージェント・コーディング系で伸び幅が大きい
- 実行時間・出力長の短縮により、**同じタスクが安く速くなる**方向のアップデート
- コンテキスト窓 100 万 tokens、max_tokens ≥ 256K が推奨
- 競合では Opus 5 に次ぐが、Apex Bench など一部で逆転。コスト次第で有力な選択肢
- ライセンスは MIT で実質制約なし
