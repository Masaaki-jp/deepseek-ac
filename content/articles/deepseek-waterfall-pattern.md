## リード

ウォーターフォール開発は「ドキュメント量が多い」「工程ごとに成果物が固定される」という特徴があり、実はLLMと相性がいい。本記事では DeepSeek V4-Pro を各工程にどう差し込むかを、工程別のプロンプト設計とコード例で示す。

## 前提

- 想定読者: 受託・社内SIでウォーターフォール工程に携わるエンジニア
- 必要な環境: Python 3.10+、`openai` SDK（DeepSeekはOpenAI互換APIを提供）
- 前提知識: Chat Completions APIの基本、工程成果物（要件定義書・設計書・テスト仕様書）の読み方

> モデル名・料金・パラメータ仕様は変更が速い。本記事のコードは執筆時点（2026年11月）の公開情報に基づく。実際に組み込む前に公式ドキュメントで最新仕様を確認してほしい。

## なぜウォーターフォールとDeepSeek Proの相性がいいのか

理由は3つある。

1. **長文コンテキストが効く**。V4-Proは100万トークン級のコンテキストを扱えるとされ、要件定義書・基本設計書・詳細設計書をまとめて投入した横断レビューが現実的になる。工程間の用語揺れや矛盾の検出は、ドキュメントを分割せずに見たほうが精度が出る。
2. **工程ごとに「正解の形」が決まっている**。ウォーターフォールは成果物のフォーマットが安定しているため、出力をJSONや表形式に固定しやすく、後工程への自動連携がしやすい。
3. **thinking modeの強弱を使い分けられる**。要件の抜け漏れ検出のような推論寄りタスクは深く考えさせ、リリースノート整形のような作業は标准モードで回す、といったコスト配分ができる。

逆に、アジャイルのように仕様が毎日変わる場面では、本記事のパターンは過剰になる。成果物が安定している工程に向けたパターンだと思ってほしい。

## 共通のセットアップ

```python
from openai import OpenAI

client = OpenAI(
    api_key="YOUR_DEEPSEEK_API_KEY",   # 環境変数から読むこと
    base_url="https://api.deepseek.com",
)

def ask(prompt: str, *, deep: bool = False, json_mode: bool = False) -> str:
    body = {
        "model": "deepseek-v4-pro",
        "messages": [{"role": "user", "content": prompt}],
        "extra_body": {
            "thinking": {"type": "enabled" if deep else "disabled"},
        },
    }
    if deep:
        body["extra_body"]["reasoning_effort"] = "high"
    if json_mode:
        body["response_format"] = {"type": "json_object"}
    res = client.chat.completions.create(**body)
    return res.choices[0].message.content
```

APIキーは必ず環境変数かシークレットマネージャから渡す。設計書をプロンプトに載せる都合上、キー漏洩＝顧客ドキュメント漏洩に直結する。

### thinking modeの使い分け

| 工程 | タスク | thinking | 理由 |
|---|---|---|---|
| 要件定義 | 抜け漏れ・矛盾検出 | 有効（high） | 多段の推論が必要 |
| 設計 | 観点別レビュー | 有効 | 判断根拠を残したい |
| 設計 | 帳票・項目名の整形 | 無効 | 作業なので過剰 |
| 実装 | 単体テスト下書き | 有効 | 境界値の網羅に推論が要る |
| リリース | 手順書の体裁統一 | 無効 | コスト優先 |

> `thinking` と `reasoning_effort` の正確な値域、および thinking 有効時に `temperature` が無視されるかどうかは公式ドキュメントで確認すること。推論系モデルでは sampling パラメータが効かない設計のものが多い。

## 工程1: 要件定義 — 抜け漏れ検出と非機能要件の洗い出し

要件定義書のドラフトを丸ごと投入し、レビュー観点を固定して指摘させる。ポイントは**出力を機械可読なJSONに固定する**こと。指摘一覧をそのまま課題管理表に流せる。

```python
REVIEW_PROMPT = """\
あなたはSIerの要件定義レビュアーです。以下の要件定義書を読み、
観点ごとに不足・矛盾・曖昧さを指摘してください。

# 観点
- 機能要件の抜け（CRUDの欠落、例外系の未定義）
- 非機能要件（性能・可用性・セキュリティ・運用・移行）
- 用語の揺れ、主語の欠落
- 上流の業務要件との対応が不明な箇所

# 出力形式（JSONのみ）
{{"findings": [{{"id": 1, "severity": "high|mid|low",
  "section": "該当章", "issue": "指摘", "question": "顧客への確認事項"}}]}}

# 要件定義書
{document}
"""
```

`question` フィールドを必ず出させるのがコツだ。「指摘」で終わらせると現場で動けないが、「顧客に何を確認するか」まで書かせると、そのままヒアリングシートになる。

## 工程2: 設計 — 設計書の横断レビューとIF整合性チェック

工程1で作った要件定義書と詳細設計書を**同時に**投入する。ここが長文コンテキストの本領で、要件→設計のトレーサビリティを機械的に照合できる。

```python
def cross_review(requirements: str, design: str) -> str:
    prompt = f"""\
次の要件定義書と詳細設計書を照合し、以下を出力してください。

1. 要件のうち設計に落ちていないもの（未トレース）
2. 設計にあるが要件に存在しない機能（スコープ外の混入）
3. 外部IF（API・ファイル連携）の項目名・型・必須可否の不一致

# 要件定義書
{requirements}

# 詳細設計書
{design}
"""
    return ask(prompt, deep=True)
```

このパターンは「AIに設計させる」のではなく「**AIに突き合わせさせる**」ことに価値がある。設計判断そのものは人間が持ち、整合性の機械的チェックだけを委ねる。レビュー記録として残せるのも大きい。

## 工程3: 実装 — 規約準拠チェックと単体テストの下書き

実装工程では、コード生成よりも**既存コード規約との突き合わせ**と**テスト観点の導出**に効く。設計書の該当章とコードをペアで渡す。

```python
def test_design(design_section: str, code: str) -> str:
    prompt = f"""\
以下の詳細設計と実装コードを読み、単体テストケースを表形式で列挙してください。
正常系・異常系・境界値・null/空文字・桁溢れ・同時実行を含めること。
設計に書かれていない仕様が必要と判断した場合は「要確認」と明記すること。

# 詳細設計
{design_section}

# 実装
{code}
"""
    return ask(prompt, deep=True)
```

「要確認」を明示させるのが重要で、これを書かせないとAIが勝手に仕様を補完して、テスト仕様書に根拠のないケースが混ざる。

## 工程4: テスト — トレーサビリティマトリクス生成

要件ID × テストケースIDの対応表を生成させる。監査対応や品質ゲートで求められる成果物を、半自動で作れる。

```python
def traceability(req_json: str, test_json: str) -> str:
    prompt = f"""\
要件一覧とテストケース一覧を突き合わせ、トレーサビリティマトリクスを作成してください。
テストが存在しない要件は covered: false としてください。
出力はJSONで: {{"rows":[{{"req_id":"","test_ids":[],"covered":true}}]}}

# 要件一覧
{req_json}

# テストケース一覧
{test_json}
"""
    return ask(prompt, json_mode=True)
```

## 工程5: リリース・運用 — 手順書とランブック

リリース手順書の体裁統一、ロールバック条件の抜け検出、障害時のランブック初版作成。ここはthinkingを切ってコストを抑える。工程1〜4で作った成果物を入力にできるので、追加のインプットはほぼ不要。

## 工程をまたぐ設計判断: どこをAIに任せ、どこを人間が持つか

| 任せる | 人間が持つ |
|---|---|
| 観点別の網羅チェック | 観点そのものの定義 |
| 要件↔設計↔テストの突き合わせ | トレードオフの決定（性能 vs コスト等） |
| 成果物の体裁統一・言い換え | 顧客合意・契約上の責任 |
| テストケースの初期網羅 | テストの採否と優先度 |

AIの出力は「レビュー記録の下書き」として扱い、承認フローは従来どおり人間が通す。監査上もこの建て付けのほうが説明しやすい。

## つまずきポイント

| 症状 | 対処 |
|---|---|
| ツール呼び出しとthinking併用で400エラー | マルチターン時に `reasoning_content` を保持して履歴に含める。落とすと不整合になる |
| 出力JSONが壊れて `json.loads` で落ちる | `response_format` の対応状況を公式で確認。不安定ならパース失敗時のリトライとスキーマ検証を入れる |
| 設計書に書いた指示文が実行される | ドキュメント内の命令文を「データ」として扱うようプロンプトで明示。プロンプトインジェクション対策は別記事参照 |
| モデル更新でレビュー結果が変わる | 評価用の固定入力セットを用意し、更新時に差分を確認する運用にする |
| 顧客ドキュメントを外部APIに送ってよいか迷う | 契約・NDA・データ所在地を先に確認。判断がつくまで匿名化データで検証する |

> 料金（入力・出力のトークン単価）は時期によって変動し、割引キャンペーンも実施される。コスト試算は必ず公式の料金ページの最新値で行うこと。

## まとめ

- ウォーターフォールは成果物フォーマットが安定しているため、LLMの出力をJSON等に固定しやすく自動連携に向く
- 長文コンテキストは「設計させる」より「要件・設計・テストを突き合わせさせる」用途でこそ効く
- thinking modeは推論寄りタスク（抜け漏れ検出・テスト導出）に限定し、整形作業では切ってコストを抑える
- 「要確認」を出力させる設計にすると、AIの勝手な仕様補完を抑えられる
- 最終承認・顧客合意・トレードオフ判断は人間側に残す
