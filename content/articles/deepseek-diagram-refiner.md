## リード

記事から講座動画を作るパイプラインに、生成した図をDeepSeek自身に直させるループを組み込みました。合格判定はLLMではなくコードが数値で行い、落ちた図だけをAPIに渡します。図1枚あたり約2回の呼び出し、0.05〜0.12セントで収まりました。

## 前提

- 想定読者: LLMに生成物を自己修正させたいエンジニア。プロンプト改善が頭打ちになった経験がある人
- 必要な環境: Python 3.x、DeepSeek APIキー、mermaid-cli（mmdc）11.16.0、描画用Chrome
- 前提知識: Mermaid記法、JSONスキーマによる検証、ツール呼び出し（function calling）の基本

## パイプラインの全体像

パイプラインは `run.sh` ひとつで、記事1本を動画にして公開するところまで実行します。DeepSeekを呼ぶのは3か所だけです。

| 工程 | DeepSeekの役割 | 出力 |
|---|---|---|
| 抽出 | 記事を読み、スライド構成とナレーション原稿を作る | `deck_ir.json` |
| 図の改善（今回追加） | 不合格の図だけを直す | 修正案JSON |
| 音声合成 | ナレーションを音声化する | 音声ファイル |

抽出より後ろは、`deck_ir.json` を受け取って毎回同じように描く決まった処理です。この「LLMは判断、コードは実行」の分け方が、以降のすべての土台になります。

## ステップ1：図の種類を内容で選ばせる

図の種類は3つに絞り、どれにするかをDeepSeekに内容から選ばせました。種類を増やすと、描画の崩れを確認する組み合わせが増えるためです。

| 図の種類 | 要点がこれのとき |
|---|---|
| シーケンス図 | 誰が誰に何を送るか |
| 状態遷移図 | 今どの状態か、どう移るか |
| フローチャート | 上記以外、迷ったとき |

抽出プロンプトにこの表を入れ、「誰が誰に送るかが要点ならシーケンス図、今どの状態かが要点なら状態遷移図、迷ったらフローチャート」と判断基準を明記します。JSONには「選んだ種類」と「選んだ理由」を入れさせますが、申告は信じません。Mermaidコードの先頭行を見て、コード側で判定し直します。

タイムライン図も候補でしたが、試すと文字が小さく余白が大きくなりました。文字サイズの設定も効かなかったため採用を見送り、時系列は「出来事を古い順に矢印でつなぐフローチャート」で描いています。

## ステップ2：Mermaidを手元で描く

描画を外部サービスの mermaid.ink から、ローカルの mermaid-cli（mmdc）に切り替えました。503エラーで待たされることがなくなり、Mermaidのバージョンも自分で固定できます。

```bash
npm install @mermaid-js/mermaid-cli@11.16.0
```

導入時には Dependency の隔離を意識しました。

- サイト本体の `package.json` には入れず、`tools/video/mermaid/` に別の `package.json` を置いた。描画用Chromeを含む重い依存を、サイトのCIに入れないため
- バージョンは 11.16.0 に固定。Renovateでもこのパッケージだけ自動マージを外した。更新で図の見た目が変わることがあるため

### 白黒で描いてから反転する

スライドは暗い背景に白い線と文字で図を載せています。そこで、どの種類の図も「白い背景に黒い線」で描き、画像の明るさをそのまま透明度に変換しています。黒は不透明な白、白は透明になるので、図の種類によらず見た目が揃い、線の縁もなめらかになります。

### 捨てる基準を「動画上の文字の大きさ」に変える

以前は描いた図の縦横比が2.4を超えたら捨てていました。この基準だと、もともと縦長のシーケンス図ほど捨てられます。

変更後は、図をスライドの置き場所に収めたときに「1920px幅の動画で文字が何pxになるか」を計算し、16px未満なら捨てます。フローチャートと状態遷移図は縦向き・横向きの両方で描き、文字が大きくなるほうを採用します。これで、縦横比のせいで捨てられていた一直線の判定図も、横向きにして使えるようになりました。

## ステップ3：抽出の質を上げる

図が少ない原因は、描き方ではなく記事の渡し方にありました。ツール呼び出しの解説記事で試すと、図5枚のうち中身は実質2種類で、「呼び出しループ」の図が3回出てきます。

抽出は記事をいくつかの塊に分け、1塊ずつDeepSeekに渡します。そのため前の塊で何を作ったかを知らないまま、リードと本文のそれぞれで同じ図を作っていました。さらに「本文」の下に約4,000字がまとめて入り、1回の呼び出しで最大5枚を詰め込んでいました。

直したのは4点です。

| 変更 | 内容 |
|---|---|
| 小見出し（`###`）でも区切る | コードブロック内の `#` は見出しと見なさず、フロントマターも渡さない。枚数の目安は「小見出し1つにつき1枚以上」 |
| 作成済みスライド一覧を次の塊に渡す | 「モデルは実行しない（図: sequence）」のような一覧と記事全体の見出しを渡し、「同じテーマ・同じ図を作らない」と指示 |
| 要約セクションは1枚まで・図なし | リード・前提・まとめ・チェックリストに印を付け、本文の内容を先取りさせない |
| 比較レイアウトを追加 | 「向く用途と慎重な用途」のような対比は、MermaidではなくPowerPointに直接描く左右2列に。1項目14文字まで |

結果、13枚すべてが別テーマになり、記事の小見出しの順に並びました。ただし図の割合を無理に上げると意味の薄い図が増えます。前提やチェックリストのようにもともと一覧の内容は、箇条書きのままにしています。

## 設計の分かれ道：DeepSeekを中心に据える

ここまでは人がログと画像を見て「細長い」「文字を縦線が貫いている」と判断し、コードを直していました。この方針を決め直し、その判断ごとDeepSeekに任せることにします。

汎用のAIエージェントにスライド作りを丸ごと任せれば、描画まで含めて柔軟にこなします。ただしそれでは、中で何が起きているかが見えません。DeepSeek APIの講座で見せたいのは「LLMには判断だけをさせ、結果をJSONで受け取って検証し、描くのは決まった処理」という分け方そのものです。

| 担当 | やること |
|---|---|
| DeepSeek | どう直すか、2段に折り返すか、分割するか、図をやめるかを判断する |
| コード | 文字の大きさ、画面の使い方、要素の数、取りこぼしの有無を判定する。合格しなければ採用しない |

このパイプラインには、サイトで解説しているテーマがそのまま入っています。JSON出力、スキーマ検証、再試行、プロンプトのファイル管理、出力ゲート、そしてツール呼び出しと予算ガードです。パイプライン自体が講座の実例になっています。

## ステップ4：ツール呼び出しで図を直させる

抽出とスライド作成のあいだに「図の改善」（`refine.py`）を追加しました。コードが全図を判定し、不合格の図だけをDeepSeekに渡します。合格した図ではAPIを呼びません。渡すツールは2つで、いずれも「修正案を出す」ためのものです（ツール定義の詳細は実装依存のため本記事では割愛します）。

判定結果は数字と日本語のヒントで返します。横一列に細長い図なら、次のような応答です。

```json
{
  "verdict": "fail",
  "problems": ["画面の使い方が小さすぎます（面積の14%、25%以上が必要）"],
  "hints": ["横一列に細長くなっています。subgraph を2つ作って各段を direction LR にし、subgraph どうしを矢印でつないで2段に折り返してください"],
  "font_px": 26.0,
  "fill_ratio": 0.14
}
```

提出された図も信じません。コードが描き直して判定し、不合格なら採用せず元の図を残します。

### 安全装置

- 1枚あたりの描画は3回まで、1実行あたりのAPI呼び出しは30回まで
- 呼ぶ前に既存の `usage.py` で日次・時間あたりの予算を確認し、呼んだあとに使用量を記録する
- 混雑（429・5xx）とタイムアウトは待ち時間を伸ばして再試行し、400は再試行しない
- どこで失敗しても元の図が残り、動画づくりは止まらない。直す前の計画は別ファイルに残す

### 実際に動かした結果

ツール呼び出しの解説記事では、横一列に細長い2枚が不合格になりました。DeepSeekはどちらも、1回描いて合格を確かめてから提出しています。API呼び出しは合計4回、費用は0.11セント（$0.0011）でした。

折り返した2段には「モデル側」「アプリ側」という名前が付きました。プロンプトで例示したグループ名の付け方を、「モデルが返すのは要求で、実行するかはアプリが決める」という記事の主張に合う形で使っています。

## ステップ5：全体図と分解図に分ける

最初の悩みだった「複雑な構成図は捨てる」を、同じ仕組みの上で解決しました。複雑すぎる図は、DeepSeekが「全体図1枚＋分解図2〜4枚」に分けて提出します。

全体図を「小さい文字で全部載せた図」にする案もありました。ただ動画の視聴者は拡大できないため、各グループを1つの箱にまとめ、文字を大きいまま保つ形を選びました。

### 複雑すぎる図の検出

文字の大きさだけでは足りません。ごちゃついた図でも、文字が16pxをわずかに超えれば合格してしまうからです。そこで要素の数も判定に加えました。

| 図の種類 | 上限 |
|---|---|
| フローチャート | 8ノード |
| シーケンス図 | 10メッセージ |
| 状態遷移図 | 7状態 |

コードは次の3つをすべて満たしたときだけ分割を採用します。

1. 全体図と分解図が、それぞれ判定に合格する
2. 元の図の要素が、どれかの分解図に同じ名前で入っている（取りこぼしがない）
3. 各スライドに2〜4文のナレーションがある

取りこぼしの確認があるので、分割で内容が減ることはありません。試験でわざと「記録」を入れ忘れた案を出すと、「元の図の要素が分解図に入っていません: 記録」と返り、不合格になりました。

### 実際に動かした結果

13ノードのパイプライン全体図で試しました。分割前は文字が15.8pxで判定に落ち、「構成・映像・公開」の箇条書きになっていました。

DeepSeekは1回目の確認で合格する案を出し、API呼び出し2回、費用0.12セント（$0.0012）で、全体図1枚と分解図3枚に分けました。元の13ノードはすべてどれかの分解図に入り、各分解図の端には前後の工程が箱として置かれています。全体図のナレーションは「この後、それぞれの工程を順に見ていきます」で終わり、分解図へ自然につながります。

ひとつだけコード側の不具合が見つかりました。DeepSeekが横向きで書いた全体図を、コードが縦向きから先に試して縦一列にしていたのです。現在は書いた向きから先に試し、読みやすさが同じならその向きを残すようにしています。

なお、通常の記事ではDeepSeekが最初から小さな図を書くため、分割はほとんど起きません。大きな構成図を説明したい記事でだけ働く仕組みです。

## つまずきポイント

| 症状 | 対処 |
|---|---|
| 幅800pxを超える図が勝手に縮む | mmdcの初期設定で横長の図が800pxに縮められる。`useMaxWidth: false` を設定する |
| シーケンス図の縦線が文字を貫く | 隣でない相手へのメッセージで、間にいる登場人物の縦線が文字の上を通る。文字に背景色の縁取りを付けて隠す |
| シーケンス図だけ文字が小さい | 文字サイズはテーマ設定ではなく、設定の最外周にある `fontSize` で決まる |
| 「文字36px」と計算したのに実際は24px程度 | 縮小の設定漏れ。判定前に実際の画像サイズを確認する |
| 判定は合格なのに図が読みにくい | 要素数の上限を追加する。文字サイズだけではごちゃついた図を弾けない |

## まとめ

- 合否はコードが決める。LLMに「読みやすいか」を聞くより、文字の大きさや要素の数を計って数字で返すほうが、安定して安く済む
- ヒントを返すと一発で直る。不合格の理由と具体的な直し方をセットで返すと、ほぼ1回の描画で合格案が出てくる
- 測る側のバグに注意。幅800pxで縮む問題や向きを勝手に変える問題があると、LLMはそれを前提に動いてしまう。判定の数字は実際の画像と見比べる
- 失敗しても止めない。図の改善は失敗しても元の図で続けられるようにし、DeepSeekのサーバーが混んでいても動画は完成する
- 費用は図1枚あたり約2回・0.05〜0.12セント。ただし単価はモデルとキャッシュヒット率で変わるため、自分の `usage` で確認する
