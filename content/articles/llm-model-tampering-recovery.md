## リード

「出力がおかしい」と感じたとき、モデル本体の汚染と自前パイプラインの汚染を切り分けないと復旧は失敗します。
この記事では、証拠保全 → 切り分け → ロールバック → 再ベースラインの順で、判断と作業を整理します。

## 前提

- 想定読者: DeepSeek API を本番または社内ツールで使っているエンジニア
- 必要な環境: Python 3.10 以上、Git 管理されたプロンプト/設定、RAG を使う場合はインデックスのスナップショット
- 前提知識: チャットAPIのメッセージ構造（`role` / `tool_calls` / `tool_call_id`）

## 本文

### 前提: 汚染されたモデルは「治療」できない

まず期待値を合わせます。ETH Zurich の研究（2025年2月）は、学習データに混入した悪性データを**後から除去するのが極めて困難**であることを示しています。つまり、

- プロバイダ側のモデル本体が汚染されていた場合、利用者側にできるのは**検知して切り離す**ことだけ
- 「汚染を消すプロンプト」や「浄化ツール」を謳うものは、まず疑ってください

復旧とは「治すこと」ではなく、**既知の正常な状態に戻して、同じ事故が起きたと分かる状態にする**ことです。

### 手順0: 何が改ざんされたのかを4層に分ける

原因の層を間違えると、正しい対処がすべて空振りになります。

| 層 | 例 | 利用者ができること |
|---|---|---|
| モデル本体（プロバイダ側） | 学習データ汚染、配信モデルの差し替え | 切り分けて報告・切替。修復は不可 |
| 自前の学習/微調整データ | 汚染コーパスでファインチューニング | 汚染チェックポイントの特定、クリーンコーパスから再学習 |
| RAG ナレッジ・ツール出力 | 参照文書への埋め込み、外部APIの応答経由の指示文 | 差分確認、インデックス再構築、出所の検証 |
| 会話履歴・セッション | 途中で壊れた `tool_calls`、改変された履歴 | 整合性チェックと切り詰め |

実務では**下の2層が原因のことが圧倒的に多い**です。上から疑うと時間を浪費します。

### 手順1: 凍結と証拠保全

最初にやるのは調査ではなく保全です。同じ入力を再実行すると、壊れた状態が上書きされて証拠が消えます。

保存すべきもの:

- リクエストID、モデル名とバージョン、日時
- `temperature` / `top_p` / `seed` などのパラメータ
- システムプロンプト全文
- RAG が参照したドキュメントの ID と版
- 生のレスポンス（JSON そのまま）と、その SHA-256

```python
import hashlib, json, datetime, pathlib

def preserve_evidence(request_id, model, params, system_prompt, response, docs):
    record = {
        "request_id": request_id,
        "model": model,
        "params": params,
        "system_prompt": system_prompt,
        "referenced_docs": docs,
        "captured_at": datetime.datetime.now(datetime.UTC).isoformat(),
        "response": response,
    }
    body = json.dumps(record, ensure_ascii=False, sort_keys=True)
    digest = hashlib.sha256(body.encode()).hexdigest()

    out = pathlib.Path("incident") / f"{request_id}.json"
    out.parent.mkdir(exist_ok=True)
    out.write_text(body, encoding="utf-8")
    (out.with_suffix(".sha256")).write_text(digest, encoding="utf-8")
    return digest
```

`sort_keys=True` は、後で突き合わせるときに差分を安定させるためです。

### 手順2: モデル側かパイプライン側かを A/B で切り分ける

同じ入力・同じパラメータで、条件だけを変えて比較します。**モデル版とパラメータは固定**してください。

| 条件 | 異常が再現するなら |
|---|---|
| 本番と同じ構成 | （基準） |
| RAG を外す / ツールを外す | 自前のナレッジ・ツール出力が原因 |
| システムプロンプトを最小構成にする | プロンプト側の問題 |
| 別の API キー・別リージョン | キー/経路側の問題 |
| モデル版を1つ前に固定 | モデル更新が契機 |
| 上記すべてで再現 | プロバイダ側を疑い、報告と切替を検討 |

「RAG を外したら直った」なら、モデルの汚染を疑う必要はありません。

### 手順3: RAG とツール出力を検査する

参照文書の差分確認は、泥臭いですが最も効きます。

- 追加・更新日時がインシデント直前に集中していないか
- 更新者が想定どおりか
- 本文に「以前の指示を無視」「以下の手順を実行」のような**指示文が混入**していないか

ツール出力も同様です。外部APIやスクレイピング結果は、**データではなく命令として読まれてしまう**経路です（間接プロンプトインジェクション）。取り込んだテキストは必ず「引用データ」として区切り、指示として解釈させない構造にしてください。

### 手順4: 会話履歴の整合性を確認する

見落としやすいのがこれです。アシスタントが `tool_calls` を返したのに、対応する `tool` 応答が欠けている（または ID が一致しない）と、**以降の全リクエストがエラーになり続けます**。1回のツール失敗が、履歴全体を恒久的に壊すわけです。

まず壊れた境界を特定し、そこから先を切り捨てて再開します。

```python
def recovery_boundary(messages: list[dict]) -> int | None:
    """履歴が壊れ始めるインデックスを返す。問題なければ None。"""
    pending: dict[str, int] = {}  # tool_call_id -> assistant メッセージの位置

    for i, m in enumerate(messages):
        if m.get("role") == "assistant" and m.get("tool_calls"):
            for call in m["tool_calls"]:
                pending[call["id"]] = i
        elif m.get("role") == "tool":
            cid = m.get("tool_call_id")
            if cid not in pending:
                return i     # 呼び出しに対応しない tool 応答
            del pending[cid]

    if pending:
        return min(pending.values())  # 応答が返っていない呼び出し
    return None


boundary = recovery_boundary(messages)
safe_messages = messages if boundary is None else messages[:boundary]
```

注意点が2つあります。

- 壊れたメッセージを**中間から1件だけ削除しない**でください。後続がそれを参照している可能性があります。必ず「そこから先を捨てる」。
- 壊れたペイロードを**そのままリトライし続けない**でください。無駄な課金とレート制限の原因になります。

そして、履歴を外部から読み込む設計（エクスポート/インポート、共有リンク、ログ再生）にしている場合は、**改変された履歴をそのまま信頼しない**前提に変えてください。

### 手順5: 既知の正常状態に戻す

切り分けが済んだら、層ごとに戻します。

1. **モデル版を固定**する（日付・バージョンを明示。更新追随は別途、評価を通してから）
2. **システムプロンプトと設定を Git で管理**し、直前のタグに戻す
3. **RAG インデックスをスナップショットから再構築**する（差分修正ではなく全再構築。汚染の取りこぼしを避けるため）
4. **API キーとトークンをローテーション**する
5. 外部から取り込むツールについては、**出所の許可リスト**を設定する

### 手順6: 復旧ツールを名乗る第三者プラグインに注意

「poisoned DeepSeek session」のような語で検索すると、**第三者が運営するプラグインレジストリ**が上位に出てきます。そこには「Security: PASSED」「Risk: LOW」といった表示とともに、GitHub リポジトリを一行で導入するコマンドが並んでいます。

これは**導入しないでください**。理由は明確です。

- レジストリは公式ではなく、表示されているスキャン結果は**配布側の自己申告に近いシグナル**
- 実行するのは**個人リポジトリのコード**で、認証情報や会話ログに触れる位置で動く
- 「復旧」「診断」を謳うツールは、まさに**侵害された環境で信頼を得やすい**

どうしても検証したい場合は、リポジトリを clone して**コミットを固定**し、コードを読み、ネットワークを切ったサンドボックスで実行してください。「レジストリで PASSED だったから安全」は根拠になりません。

なお、本記事の手順4の検査は、こうした外部プラグインに頼らず 30 行程度で自前実装できます。**復旧作業に外部依存を持ち込まない**のが原則です。

> モデル名・API仕様・レート制限などの最新値は記憶に頼らず、公式ドキュメントで確認してください。

### 手順7: 再ベースラインと監視

復旧の完了条件は「動いた」ではなく「**異常を検知できる状態に戻った**」です。

- 固定の評価セット（正常系50件 + 敵対系20件程度）を用意し、復旧前後でスコアを比較
- 定型応答の埋め込み距離を日次で記録し、急変をアラートに
- 特定トピックだけ挙動が違う場合は、そのトピックを重点的にサンプリング監視

もし**個人データの漏えい**を伴うインシデントだった場合は、GDPR などの通知義務の対象になり得ます。技術的復旧と並行して法務確認を走らせてください（詳細は法務・規制シリーズで扱います）。

## つまずきポイント

| 症状 | 対処 |
|---|---|
| 再現しようとしたら直った | 証拠を保全できていない可能性。まず手順1のログ整備から |
| 特定の話題だけおかしい | モデル汚染より RAG 文書の混入を先に疑う |
| 履歴の途中から全リクエストが失敗する | `tool_calls` と `tool_call_id` の不整合。手順4で境界を特定して切り詰める |
| モデル版を上げた直後から挙動が変わった | 版を固定して評価セットで比較。ロールバックを先に |
| 浄化系のツールを見つけた | 導入前にソースを読む。閉じたモデルの汚染は消せない前提で判断 |

## まとめ

- 汚染されたモデルは「治療」できない。復旧とは切り離して正常状態に戻すこと
- 原因はモデル本体より RAG・ツール出力・会話履歴にあることが多い
- 証拠保全を最優先し、再実行で証拠を上書きしない
- 復旧作業に未検証の第三者プラグインを持ち込まない
- 完了条件は「動くこと」ではなく「異常を検知できること」
